Hubini — WebSocket Connection Flow


Step 1
Device Opens a Connection

The device connects to the server over WebSocket at the address below. No data is sent yet — just the connection itself.

wss://hubini-homes.onrender.com/ws

As soon as the connection is made, the server assigns it a temporary unique ID (a UUID) so it can track this socket even before the device has identified itself.

The server also sends back a welcome message right away:
{ type: "connected", message: "Connected to Hubini WebSocket. Please authenticate." }
Step 2
Device Identifies Itself

After connecting, the device must immediately send its Cloud ID to the server so the server knows which device this socket belongs to.

The message format is a plain string — not JSON:

MeWs|DEV_XXXXXXXXXXXXXXXXXX

The part before the pipe (|) is always MeWs. The part after is the device's Cloud ID, which starts with DEV_.

Once the server receives this, it maps the socket to that Cloud ID and marks the device as online in the database.

The server responds with:

{ "type": "registered", "cloudId": "DEV_XXXXXXXXXXXXXXXXXX" }
Step 3
Server Can Now Send Commands

Once the device is registered, the server can push commands to it at any time. Commands come in this format:

{ "type": "command", "command": "ON" }

The command value is whatever was set up when the device was registered (stored in the Trigs field). The device should read this field and act on it.

Step 4
Device Reports a State Change (Optional)

If the device needs to report its current state back to the server (e.g. a sensor reading, or confirming a command was executed), it sends:

{ "type": "device_state", "cloudId": "DEV_XXXXXXXXXXXXXXXXXX", "state": "ON" }

The server will update the database and notify the owner's app in real time.

Step 5
Keeping the Connection Alive

The server pings every connected socket every 30 seconds. The WebSocket library handles the pong response automatically — the device firmware doesn't need to do anything special for this.

If a device doesn't respond to the ping, the server will close the connection and mark the device as offline.

If the device wants to send its own heartbeat, it can send:
{ type: "heartbeat" } — the server will respond with { type: "heartbeat_ack" }
Summary
Message Reference
Direction Message When
Device → Server MeWs|DEV_XXX Right after connecting. Identifies the device.
Server → Device { type: "registered" } Confirms the device is recognized.
Server → Device { type: "command" } Sent when a user triggers the device from the app.
Device → Server { type: "device_state" } Device reports its current state.
Device → Server { type: "heartbeat" } Optional. Keeps the connection alive manually.
